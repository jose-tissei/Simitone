# Injecting lighting, shadows and anti-aliasing into Simitone

Anti-aliasing and richer real-time lighting are both feasible by injection on v0.8.12. Hardware ray tracing is not, at least not for the 2D sprite modes. The best return is a post-process SMAA or FXAA pass at the existing world-to-screen blit, followed by depth-derived normals and Radiance Cascades global illumination built from the room layout. The release is a .NET Framework 4.x build on a custom FSOMonoGame fork. It ships precompiled effects, and its DLLs already expose the public seams a Cecil hook needs. Stock MonoGame has no compute shaders, UAVs or DXR, and no source shows DXR working from MonoGame. Sprites carry colour, a packed depth texture and a world position, but no normals. Simitone already forces Ultra lighting (mode 3), so real-time shadows already exist as a baked per-floor 2D light map. The practical plan is therefore to extend that light map and add pixel-shader passes, not to build a ray tracer. Sections below give the evidence, the ranked order and the spikes. Almost everything here is code reading, and no runtime profiling has been done. Frame-time figures other than those cited are estimates and must be measured.

## The shipped renderer exposes clean seams for injection

The frame is owned by `FSO.LotView.World`. `PreDraw` renders the whole lot into a private full-screen target, `PPXDepthEngine.Backbuffer`, and `Draw` only blits that target to the screen. The UI layer draws afterwards (`GameScreen.cs:203-226`, `World.cs:646-702`). That blit, `PPXDepthEngine.DrawBackbuffer`, is the natural place for an AA or colour-grading pass, because it runs before the UI and so cannot blur text. It also has a replaceable delegate, `SSAAFunc`, which is public static. The pipeline notes verified with Cecil that the shipped DLLs match the source for `World.InternalDraw`, `PPXDepthEngine` and `WorldContent`. That includes `World.Draw` and `InternalDraw` as public/protected virtuals, `WorldState.PrepareLighting` as the point where light textures are handed to every shader, and `PPXDepthEngine.GetBackbuffer()` as a public static. The existing `SpriteCardsPatch` already shows the three insertion styles needed: a prefix call, a call replacement, and a call before every `ret`. The `SpriteCards.Apply` hook also already receives a `WorldState` per object per frame, so a new hook library can capture the device, light and camera without any new patch.

Effects are loaded from `Content\DX\Effects\*.xnb` through `WorldContent.LoadEffects`. There are 14 files, they are compiled MGFX version 8 for DX11, and no loose `.fx` ships. Replacing `SSAA.xnb` in place while keeping the parameter names `SSAASize` and `tex` gives a no-code post-effect for the SSAA path. A hook library can also build `new Effect(device, bytes)` from an embedded blob, which avoids the content pipeline altogether. The one missing piece is a shader compiler. `2MGFX.exe` is absent from this machine, no global `mgcb` or `mgfxc` is installed, and the compiler source lives in the vendored fork under `FreeSO\Other\libs\FSOMonoGame\Tools` but was never built. Compiling a custom HLSL effect to the fork's format is the first real blocker, so it is the first spike.

## Injection suffices; rebuilding from source would not even match the release

The source tree targets net9.0 with stock MonoGame 3.8.4 NuGet packages. The running game is the v0.8.12 release, with `FSO.LotView.dll` and `MonoGame.Framework.dll` on .NET Framework 4.5 and `Simitone.Windows.exe` on 4.6.1. The release has a different namespace layout, for example `FSO.Client.GlobalSettings` versus `FSO.UI` in source. The repo's own docs state that source and release differ, and CI pins v0.8.12 and builds only the tools against it. A source rebuild would therefore change the runtime, the MonoGame fork, the shader format and the type layout all at once, and none of that would drop into the existing install. One research note read the csproj and concluded the game runs stock DX11 MonoGame 3.8.4. The other note read the shipped DLL itself and found the FSOMonoGame fork, and I treat the DLL reading as authoritative. Both agree on the important consequence: shaders are limited to what the fork's DX11 path supports, with the vendored fork requesting feature levels 10_0 to 11_1 and mapping HiDef to 10_0.

I recommend injection for everything in the plan below. A rebuild is justified only if a feature needs new vertex data, such as a normal channel in `_2DSpriteVertex`, or new render targets bound inside the sprite shaders. Even then, patching the vertex format with Cecil is probably less work than switching runtime. Injection has one standing cost: hooks depend on exact method names in the release, so every patch must start from the original DLLs and be chained with the existing patchers, and each new hook needs patch tests in the style of `Tools/PatchTests`.

## Anti-aliasing: add post-process SMAA before touching anything else

Simitone has a three-state AA setting: 0 is off, 1 is 4x MSAA, 2 is 2x2 SSAA. The game never exposes SSAA, because `Program.Main` overwrites `AntiAlias` from the `-aa` flag and there is no in-game AA toggle. In the 2D camera the engine refuses SSAA and falls back to 8x MSAA (`World.cs:969-996`). There is no FXAA, SMAA or TAA anywhere. MSAA is a poor fit for this frame. It shades once per pixel, so alpha-tested sprite edges and point-sampled texture detail stay jagged ([MonoGame forum](https://community.monogame.net/t/quick-overview-how-to-work-with-msaa-directx-too/8570)). It also averages the colour-encoded depth target at edges, and it multiplies the cost of MRT rendering. Post-process AA sees only the final colour, so it smooths both sprite silhouettes and mesh edges at once.

The recommendation is SMAA 1x. Its licence is standard MIT, with a clause that binary distributions need not reproduce the notice ([iryoku/smaa](https://raw.githubusercontent.com/iryoku/smaa/master/LICENSE.txt)). It needs two precomputed lookup textures and three passes. FXAA 3.11 is a quicker one-pass stopgap, and a MonoGame forum thread reports it migrates easily ([forum](https://community.monogame.net/t/monogame-content-builder-fails-to-build-valid-shader/6885)). Its licence history is unclear: public domain for FXAA 3 and reportedly BSD-3 for 3.11 ([Wikipedia](https://en.wikipedia.com/wiki/FXAA)), so verify NVIDIA's file before shipping. The SMAA port has known pitfalls. A Urho3D thread reports wrong blend weights on D3D11 ([thread](https://discourse-urho3d.github.io/t/smaa-implementation/5646)), and one forum thread reports SMAA failing in MonoGame's content builder. The MerjTek MIT package lists SMAA and MLAA but targets DesktopGL and was not inspected. The pass must run on the colour target only, never on the colour-encoded depth or ID buffers. Cheap follow-ups are sprite sampling hygiene (premultiplied alpha, RGB dilation at silhouettes, bilinear or smooth-pixel sampling at fractional zoom, mipmaps when zoomed out) and a render-scale slider generalising the 4-tap box SSAA. Note that SSAA of point-sampled sprites cannot add texture detail; it only smooths geometry and alpha edges. TAA is a weeks-long, ghosting-prone project, because Sims, light-map updates and zoom all disturb history, so defer it. DLSS, DLAA and FSR are not worth pursuing: they need native Streamline or NGX code, signed NVIDIA DLLs, real depth and motion vectors, and FSR 4 needs DX12 ([Streamline guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuide.md), [GPUOpen](https://gpuopen.com/fidelityfx-superresolution-4/)).

## Lighting: build on the existing light map, then add radiance cascades

FreeSO's custom lighting engine already does GPU light maps with soft shadows, wall shadows from each wall line, and object shadows from collision bounds ([FreeSO blog](http://www.freeso.org/may-15th-update-brighten-your-monday/)). In the code, `LMapBatch` bakes a top-down per-floor map containing room lights, outdoor sun and shadow volumes, driven by the VM clock, and `LightingCommon.fx` samples it by world position. It has no normals, no per-pixel dynamics and no height. Ultra mode adds a 3D object shadow map. Since the whole lighting model hangs off `WorldState.PrepareLighting` and the `LightEffects` list, richer lighting can be injected by feeding better textures to the same shader parameters.

The ranking has two caveats. The cost figures marked as estimates in the research are unmeasured, and the radiance cascade numbers come from a different workload than a Sims lot.

| Rank | Technique | Cost at 1080p | Fit and constraints |
|---|---|---|---|
| 1 | Depth-derived normals plus N·L in sprite shaders | well under 1 ms (estimate) | Sprites carry packed depth, so normals come from finite differences; silhouettes need edge-aware handling |
| 2 | 2D Radiance Cascades or HRC on a plan-view occluder and emitter grid | HRC 1.85 ms at 512², 7.67 ms at 1024² on a laptop RTX 3080 (self-reported) | No denoiser, no compute needed, runs in pixel shaders; colour bleed and soft shadows; occluders come free from walls, floors, room ids and object footprints |
| 3 | GTAO or SSAO | about 0.56 ms at 1080p on an RTX 2060 (XeGTAO, MIT) | Contact darkening only; limited by what the depth buffer holds |
| 4 | Hybrid DXR shadows on proxy geometry | estimate 0.5-2 ms plus BVH build | Needs a second D3D12 device; mesh mode only |
| 5 | Voxel cone tracing, LPV, DDGI | estimate 2-6 ms | Poor fit for sprites; DDGI sits under NVIDIA's restricted SDK licence |

Radiance Cascades is the centrepiece. Sannikov's method, used for global illumination in Path of Exile 2, splits the radiance field into ranges and rebuilds it every frame with no temporal reuse, so there is no ghosting ([80.lv](https://80.lv/articles/radiance-cascades-new-approach-to-calculating-global-illumination)). It runs in a 2D flatland that matches the lot's tile grid, and the WebGL demos prove it works with pixel shaders alone ([jason.today](https://gist.github.com/jasonjmcghee/0c72d185830685f67d3b8d9c7f330c3a)). HRC makes the cost constant per scene size ([arXiv 2505.02041](https://arxiv.org/abs/2505.02041)). Since the fork has no compute, a pixel-shader implementation is required, and the DX11 path supports it. Reusable code is limited to MIT or Apache projects: sparse_rc_2d and solis_2d are dual-licensed MIT or Apache-2.0 ([sparse_rc_2d](https://awesome.ecosyste.ms/projects/github.com%2Ficekontroi%2Fsparse_rc_2d), [solis_2d](https://docs.rs/crate/solis_2d/0.1.1)). Others have no verified licence. The cascades give flatland radiance in plan view. Walls and objects occupy cells, lamps and windows become emitters, and sprites sample the result by world position. Vertical occlusion, such as an object shading a wall, needs extra height layers or a coarse 3D grid, and that part is unresolved. The output can be fed in through the existing `LightMap` textures or a new sampler added in `PrepareLighting`. Screen-space variants cannot see off-screen content and over-brighten the background, per the Chalmers thesis ([thesis](https://odr.chalmers.se/items/9e42007a-bb60-440f-ba28-04410822758f/full)), and cutaway walls make that worse.

## Ray tracing: software marching now, DXR only as a research track

No source shows DXR working from MonoGame. Maintainers said in 2019 that it was unsupported and D3D12 was far off ([forum](https://community.monogame.net/t/rtx-dxr-support/11804)). MonoGame 3.8.5 adds a WindowsDX12 target, but it moves to a native library and swaps the package, and nothing says whether it exposes DXR or the raw device ([3.8.5 post](https://monogame.net/blog/2026-07-15-3.8.5-release-2026/)). The only realistic hardware route is a second D3D12 device created with Vortice, which is how C# DXR demos work ([CSharpDirectXRaytracing](https://github.com/Jorgemagic/CSharpDirectXRaytracing)). It would build its own BLAS and TLAS from proxy geometry (wall boxes, floors, object bounds), render a visibility term into a texture shared with MonoGame's D3D11 device, and use fences for synchronisation. The fork exposes the device and a shared handle for textures, assuming those match the release. That is a large engineering effort with a denoiser still needed at one sample per pixel, and it buys little in sprite mode, where floors are mostly matte and sprites hold no reflection data. Compute fork builds exist (cpt-max, Compute NuGet packages up to 3.8.3), but they are 3.8.x forks of stock MonoGame, not of FSOMonoGame, so adopting them would replace the engine's framework DLL with unknown compatibility ([PR #7533](https://github.com/MonoGame/MonoGame/pull/7533), [guide](https://raw.githubusercontent.com/cpt-max/Docs/master/MonoGame%20Compute%20Shader%20Guide.md)). The verdict is to deliver the visible benefit of ray tracing (soft shadows, bounce light) through software cascades, and to treat DXR as a Full 3D mesh-mode experiment only after everything else is done.

## Risks, and the spikes that retire them

Rendering is isolated from simulation. The VM clock feeds `OutsideTime` one way, and Simitone is offline, so render-only changes cannot break determinism or multiplayer. The real risks are technical. Mode switching destroys and recreates screen targets via `InitScreenTargets` each time `SetGraphicsMode` runs, so every injected render target must be rebuilt on that event. `ChangeAAMode` reassigns `SSAAFunc` on every call, so an injected delegate must be re-applied afterwards. Depth differs per camera: the 2D camera uses `BackbufferDepth` and the MRT depth channel, while the 3D camera uses a hardware depth buffer that is not shader-readable in the fork. Any effect that needs depth therefore needs two code paths. A scene insertion inside `InternalDraw` can break index buffer or depth state, which is the very bug the DrawImmediate patch fixed. Finally, MSAA on the DX11 backbuffer together with the MRT depth target in Hybrid2D was never tested.

The spikes, in order, are these. First, build a shader toolchain: get the fork's 2MGFX building, or find an MGFX v8-compatible compiler, and replace `SSAA.xnb` with a test shader to prove the load works. Second, prototype a post pass: Cecil-patch `PPXDepthEngine.DrawBackbuffer` or set `SSAAFunc` from a hook library, run FXAA first and then SMAA 1x on the backbuffer, and verify with the existing simtool screenshots and e2e scripts. Third, time a full-screen test shader on the real GPU, because the GPU model is unknown and no budget has been measured. Fourth, write a depth-to-normal pass for the 2D path and test N·L shading against `LMapBatch`. Fifth, build the plan-view occluder and emitter grid from the blueprint and port a pixel-shader Radiance Cascades merge from sparse_rc_2d. Sixth, only then evaluate GTAO and a Vortice D3D12 DXR proof of concept. Whichever comes later, also check the SMAA and FXAA licence files and the MIT or Apache status of any RC repository before copying code.

## Conclusion

The central finding is that the engine's constraints, not the GPU, set the ceiling: a DX11 fork with no compute, no readable depth and no normals. That favours techniques designed for exactly that regime, namely morphological AA on the final colour and cascaded probes marched in pixel shaders over the room grid. Because the blit-to-screen seam and the light-map seam are both public and already hooked in spirit by existing patches, the work can ship as a second injected library without touching the repo's source or the runtime.

Three questions will decide the schedule. Can an MGFX v8 compiler be produced? Does the 2D camera's packed depth give usable normals? And does the unverified MSAA-plus-MRT interaction survive a post pass? If the first two answers are yes, SMAA and normal-lit sprites should be achievable in days, and Radiance Cascades GI in weeks. Treat ray tracing as a later, optional bonus that real-time GI in plan view already approximates.
